## Boundary decision

The provider execution preflight design lane is closed.

Implementation remains blocked until a separate implementation authorization boundary is designed, reviewed, and accepted.

This document designs that future authorization boundary.

This document does not grant that authorization.

## Implementation classes

A future implementation authorization boundary must name exactly which implementation class is being authorized.

Allowed future implementation classes are:

- docs-only follow-up
- static JSON fixture creation
- JSON schema creation
- TypeScript schema creation
- validation helper creation
- validation test creation
- package script wiring
- CI workflow wiring
- coverage audit helper creation
- coverage audit test creation

Any implementation class not explicitly listed in the accepted authorization boundary is blocked.

Provider execution is not an implementation class in this boundary.

Model calls are not an implementation class in this boundary.

OpenAI API use is not an implementation class in this boundary.

Runtime/API/UI wiring is not an implementation class in this boundary.

Artifact/report creation is not an implementation class in this boundary.

Publication framing is not an implementation class in this boundary.

## Authorization field requirements

A future implementation authorization boundary must explicitly set:

- `docsOnlyAuthorized`
- `staticJsonFixtureCreationAuthorized`
- `jsonSchemaCreationAuthorized`
- `typeScriptSchemaCreationAuthorized`
- `validationHelperCreationAuthorized`
- `validationTestCreationAuthorized`
- `packageScriptWiringAuthorized`
- `ciWorkflowWiringAuthorized`
- `coverageAuditHelperCreationAuthorized`
- `coverageAuditTestCreationAuthorized`
- `providerExecutionAuthorized`
- `modelCallAuthorized`
- `openAiApiUseAuthorized`
- `runtimeApiUiWiringAuthorized`
- `artifactReportCreationAuthorized`
- `publicationFramingAuthorized`

All fields default false.

Missing fields fail closed.

Unknown fields fail closed.

Ambiguous fields fail closed.

Any true field requires a named implementation class, exact file scope, exact test scope, and stop conditions.

## Required test scope

A future implementation authorization boundary must define:

- focused test command
- static validation command, if applicable
- integration test command, if applicable
- build command
- quick gate command
- full gate command, if required
- diff guard command
- changed-file guard command

If a test fails, the lane fails closed.

If a test is skipped without explicit review, the lane fails closed.

If the changed-file guard shows unexpected files, the lane fails closed.

## Required PR guard

A future implementation authorization boundary must require:

- clean repo before branch creation
- current main synced with origin/main
- no unexpected open non-dependency PRs
- source design docs present
- exact changed-file guard
- no fixture path change unless explicitly authorized
- no schema path change unless explicitly authorized
- no runtime/API/UI path change unless explicitly authorized
- no provider default change unless explicitly authorized
- no artifact/report path change unless explicitly authorized
- final PR diff check before merge
- GitHub checks stable and clean before merge
- post-merge main sync proof
- open PR proof after merge
- DF_BRAIN log and project update after merge

- repo is dirty before branch creation
- main is not synced
- unexpected non-dependency PR exists
- source docs are missing
- source docs are unreviewed
- changed files exceed authorized scope
- fixture path changes without fixture authorization
- schema path changes without schema authorization
- script path changes without helper authorization
- test path changes without test authorization
- package files change without package authorization
- CI workflow changes without CI authorization
- runtime/API/UI files change without runtime/API/UI authorization
- provider execution appears
- model call appears
- OpenAI API use appears
- hidden fallback appears
- silent rerun appears
- provider default changes
- model default changes
- endpoint default changes
- artifact/report creation appears
- publication framing appears
- evidence boundary changes
- required tests fail
- GitHub checks fail
- mergeability fails
- DF_BRAIN is dirty before update

## Provider execution boundary

Provider execution remains blocked.

The implementation authorization boundary designed here cannot authorize:

- live provider calls
- model calls
- OpenAI API calls
- Ollama calls
- any other provider calls
- network execution
- runtime/API/UI execution path
- server action execution path
- scheduled execution path
- hidden fallback execution path

A future provider execution lane must be separate.

That future lane must have its own boundary, review, authorization fields, file scope, test scope, stop conditions, and evidence boundary.

## Runtime/API/UI boundary

Runtime/API/UI wiring remains blocked.

No route, server action, UI control, background task, or scheduler may trigger provider execution under this boundary.

Any future runtime/API/UI wiring must be separately designed, reviewed, and explicitly authorized.

## Evidence boundary

This implementation authorization boundary design is:

- implementation planning evidence only
- preflight-control design evidence only
- not provider-output evidence
- not candidate-truth evidence
- not origin evidence
- not model-quality evidence
- not publication evidence
- not execution-safety evidence

Passing a future implementation boundary does not prove provider output correctness.

Passing a future implementation boundary does not prove candidate truth.

Passing a future implementation boundary does not prove origin truth.

Passing a future implementation boundary does not prove publication readiness.

Passing a future implementation boundary does not prove execution safety.
