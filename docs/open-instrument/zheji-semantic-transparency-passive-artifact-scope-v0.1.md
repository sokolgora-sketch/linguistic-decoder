## Scope decision

This document defines the passive artifact scope for Zheji Semantic Transparency Layer v0.1.

This is a scope definition only.

It does not create the passive artifacts.

It does not authorize runtime integration.

It does not authorize UI integration.

It does not authorize provider execution.

It does not authorize Zheji replay.

## Accepted passive artifact bundle

The next implementation lane may create only passive, non-runtime artifacts:

1. Passive JSON schema file.
2. Passive static fixture file.
3. Passive validation helper script.
4. Unit tests for the validation helper.
5. Documentation linking the passive artifacts back to the design contract.

These artifacts must live outside runtime/API/UI paths.

They must not be imported by production code.

They must not produce evidence packs.

They must not call a provider.

They must not replay Zheji examples through an engine or model.

## Proposed artifact paths

Allowed future paths:

* `docs/open-instrument/schemas/zheji-semantic-transparency/zheji-semantic-transparency-schema-v0.1.json`
* `docs/open-instrument/fixtures/zheji-semantic-transparency/zheji-semantic-transparency-static-fixture-v0.1.json`
* `scripts/openInstrumentZhejiSemanticTransparencyValidation.v0.1.mjs`
* `tests/openInstrument.zhejiSemanticTransparencyValidation.v0.1.spec.ts`

No other files are authorized by this scope.

## Passive schema scope

The passive schema may describe the shape of `semanticTransparency`.

The schema must include:

* `schema_version`
* `posture`
* `target_word`
* `normalized_word`
* `surface_vowels`
* `functional_vowel_path`
* `transparency_status`
* `claim_policy`
* `free_operator_candidates`
* `carrier_claims`
* `code_f`
* `code_e`
* `isolation_audit`
* `witnesses`
* `blocked_claims`
* `null_reason`
* `source_note`
* `diagnostic_notes`

The schema must remain passive.

The schema must not be used by runtime routes unless a later exact authorization says otherwise.

## Passive fixture scope

The passive fixture may contain static examples.

Allowed fixture cases:

* one candidate transparency example
* one null example
* one blocked forbidden-claim example

Fixture cases must be static.

Fixture cases must not be generated by provider output.

Fixture cases must not be represented as historical proof.

Fixture cases must not be publication evidence.

## Passive validation helper scope

The validation helper may validate static local fixture content against the passive contract.

The validation helper may check:

* required fields exist
* `claim_policy` is present
* forbidden claim labels are blocked
* `source_note` rejects origin and ownership claims
* Code F and Code E are independent fields
* null result has a null reason
* provider-only support cannot be accepted as strong evidence
* blocked forbidden claims force `blocked_forbidden_claim`
* fixture examples do not use origin/ownership/proof language

The validation helper must not:

* call network
* call OpenAI
* call Ollama
* call any local provider
* read secrets
* mutate runtime files
* write evidence packs
* generate reports
* write artifacts outside test temp output
* import runtime/API/UI code

## Unit test scope

Unit tests may run the passive validation helper against the static fixture.

Required test assertions:

* candidate transparency fixture passes
* null fixture passes
* blocked forbidden-claim fixture passes
* missing source note fails
* origin claim wording fails
* ownership claim wording fails
* provider-only strong evidence fails
* Code F / Code E coupling fails
* missing null reason fails for null status
* runtime/API/UI imports are absent

## Forbidden files

The passive artifact lane must not change:

* `app/**`
* `pages/**`
* `src/app/**`
* `src/pages/**`
* `src/ui/**`
* `src/components/**`
* `src/shared/**`
* API route files
* runtime analysis engine files
* provider execution scripts
* source-engine provenance runtime files
* evidence-pack generation files
* package metadata unless a test dependency is explicitly authorized later

## Forbidden behavior

The passive artifact lane must not:

* execute a provider
* replay Zheji examples
* call OpenAI
* call localhost/Ollama
* call remote endpoints
* read or write secrets
* change runtime behavior
* change API output
* change UI output
* create evidence packs
* create publication artifacts
* claim origin
* claim ownership
* rank candidates as truth
* promote candidates to evidence

## Required source-note meaning

Every fixture case must include a source note with this meaning:

This artifact records candidate semantic transparency and meaning-motivation only. It does not claim origin, historical ownership, final etymology, or publication-grade proof.

The exact wording may vary, but those constraints must be present.

## Accepted statuses

Allowed `transparency_status` values:

* `not_evaluated`
* `null_no_transparency`
* `insufficient_evidence`
* `candidate_transparency`
* `partial_transparency`
* `strong_candidate_transparency`
* `blocked_forbidden_claim`

No status means proven origin.

No status means linguistic ownership.

No status means provider-confirmed truth.

Forbidden implementation posture:

* publication framing
