## Status

- schema design only
- not implemented
- no source schema change
- no validator change
- no prompt change
- no runtime change
- no model call
- no artifact replay
- no provider default change

This schema design supports embryo morpheme meaning analysis. It is not external origin/truth evidence.

## Source design reviewed

This design is grounded in:

- PR #1219 design doc: `docs/open-instrument/zheji-semantic-transparency-layer-v0.1.md`
- PR #1220 review doc: `docs/open-instrument/zheji-semantic-transparency-layer-review-v0.1.md`

PR #1220 accepted the design direction. This PR converts that accepted direction into exact future field shapes.

## Current Brain candidate shape

The current required candidate fields remain:

- segmentationId
- chunk
- language
- candidateForm
- meaning
- functionFit
- sourceNote
- evidenceType
- candidateType
- falseFriendRisk
- nullCandidate
- notes

These existing enum and traceability semantics must remain unchanged. The future Zheji fields are additive only.

## Additive field placement decision

Future candidate-level fields:

- analysisLayers
- semanticTransparency

Future chunk/embryo-level computed field:

- transparencyContrast

Decision:

- Brain may return candidate-level analysisLayers and semanticTransparency.
- Brain must not return computed transparencyContrast.
- A deterministic post-processor computes transparencyContrast after candidate-level fields exist.
- Existing raw Brain output and normalized Brain output boundaries remain unchanged.

## Exact future type shapes

### ZhejiAnalysisLayers

Future shape:

- formal:
  - isPresent: boolean
  - evidenceNote: string or null
- symbolic:
  - isPresent: boolean
  - evidenceNote: string or null

Rules:

- evidenceNote must be short when isPresent is true.
- evidenceNote may be null when isPresent is false.
- if symbolic evaluation is not possible because doctrine reference is absent or incomplete, symbolic.isPresent should be false and evidenceNote should be null or a short not-evaluated note depending on validator decision.
- no nested sub-objects beyond formal and symbolic in v0.1.
- no score fields.
- no rank fields.

### ZhejiSemanticTransparency

Future shape:

- level: atomic | metaphorical | opaque
- reason: string
- decomposition: optional string array

Rules:

- reason must be short and auditable.
- decomposition is optional.
- decomposition must be a short string array if present.
- no score fields.
- no rank fields.
- no origin verdict fields.

### ZhejiTransparencyContrast

Future shape:

- hasContrast: boolean
- matrix:
  - atomic: string array
  - metaphorical: string array
  - opaque: string array

Rules:

- matrix arrays contain language labels or language codes from non-null candidates.
- no natural-language note field in v0.1.
- no winner field.
- no score field.
- no candidateType mutation.
- if candidate ids are unavailable, language-only matrix is acceptable for v0.1.
- future candidate-id support may be added only after a separate design.

## Candidate id decision

Current Open Instrument Brain candidate outputs do not have a stable candidateId in the contract.

Decision:

- do not add candidateId in this schema-addition v0.1
- use language-only matrix for transparencyContrast
- revisit candidate ids in a separate design if multiple candidates per language make matrix ambiguity problematic

## Null candidate treatment

- nullCandidates should not require semanticTransparency in v0.1.
- nullCandidates may omit analysisLayers in v0.1 unless later validator design decides otherwise.
- nullCandidates should not contribute to transparencyContrast.matrix.
- nulls remain evidence of absence, not transparency evidence.

## Required vs optional decision

Future rollout posture:

- analysisLayers and semanticTransparency should be required for non-null chunkCandidates only after schema, prompt, and validator PRs land together in a controlled sequence.
- During transition, design should allow staged artifacts where old outputs lack the fields.
- transparencyContrast should be required only in normalized or post-processed outputs, not raw Brain output.

## Validator design implications

Future validator should:

- validate field shapes
- require allowed levels only
- require short strings for notes and reasons
- reject scores, ranks, and origin verdicts
- reject prose contrast notes generated by post-processor
- ensure candidateType is not changed by transparency
- ensure transparencyContrast is absent from raw Brain output if the boundary decides Brain must not return it
- ensure computed contrast matrix uses known transparency levels

No validator changes in this PR.

## Prompt design implications

Future prompt should:

- request candidate-level analysisLayers
- request candidate-level semanticTransparency
- explicitly forbid Brain from returning transparencyContrast
- include a compact doctrine reference if symbolic evaluation is allowed
- default symbolic to false or not evaluated if doctrine reference is absent
- require short evidence notes and reasons
- forbid scoring, ranking, and origin claims
- keep local-model burden low

No prompt changes in this PR.

## Normalizer/post-processor implications

Future post-processor should:

- preserve raw Brain output
- preserve normalized Brain output
- compute transparencyContrast into a derived output object
- use only candidate-level semanticTransparency.level
- group by language into atomic, metaphorical, and opaque arrays
- avoid prose generation
- avoid winner selection
- avoid candidateType mutation
